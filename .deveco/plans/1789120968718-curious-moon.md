# mybatis-go 优化点整理 — 剩余 3 项实施计划

## Goal

实现 2026-09-04 优化点整理文档中尚未完成的 3 项：
- **M-04**：自定义 `resultType` 短类名解析（如 `resultType="SysUser"` 不再 fallback 到 `map[string]interface{}`）
- **M-07**：分页支持（`PageHelper` 等价物，含 `LIMIT/OFFSET` 自动注入 + `COUNT(*)` 总数查询）
- **4.3**：`<if test>` 字段引用静态校验（注册期检查字段是否存在，防止"空 WHERE"）

## Scope / Non-goals

**包含：**
- M-04：`SqlResult` 延迟类型解析 + `ReturnType.checkSql` 放宽
- M-07：`PageParam` 参数约定 + 代理层检测 + SQL 改写器 + COUNT 查询 + codegen `selectPage` 签名更新
- 4.3：注册期 `<if test>` 字段引用校验（仅 warning，不阻塞注册）
- 三项各自的单元测试与 SQLite 端到端测试

**不包含：**
- `lib/pq → pgx/v5` 迁移（官方评估暂缓）
- `?` 占位符方言转换优化（保持现状）
- Java OGNL 全量支持（三元/方法调用/字符串比较不在范围）
- 分页缓存/预编译缓存适配（首版不做，后续可加）

## Current State And Constraints

- **版本**：v0.2.0（基于 go 1.24.0），优化文档中 1.1~5.3 大部分项已完成
- **包依赖**：`types` 包被 `orm` 导入，`types` 不能反向导入 `orm`（import cycle 约束）
- **初始化顺序**：`orm.Initialize()` 解析 XML → 用户 `orm.RegisterModel()` 注册模型 → `orm.RegisterMapper()` 绑定函数。XML 解析时模型尚不可用，必须延迟解析
- **命名映射**：XML `<if test="tableName">` 用 camelCase；Go struct 字段用 PascalCase（`TableName`）；`buildKey` 统一小写匹配，校验工具须兼容
- **SQL 改写**：`table_prefix.go` 已有完整 tokenizer + 改写框架，LIMIT/OFFSET 注入可复用
- **测试约定**：`t.Error()` 不用 `t.Fatal()`；测试函数命名 `Test_函数名`

## Design

### M-04：自定义 resultType 短类名延迟解析

**核心思路**：参照 `resultMap` 路径已有的延迟解析模式（`ResultM.TypeName` 保留原始字符串，运行时 `gCache.createModel(name)` 解析），为 `resultType` 路径增加相同的延迟解析能力。

**改动点：**

1. **[types/sql_result.go](types/sql_result.go)**：`SqlResult` 新增 `ResultTypeName string` 字段
2. **[types/sql_result.go](types/sql_result.go)**：`parseSqlResult1` 在调用 `parseResultTypeFrom` 之前，将原始值存入 `ResultTypeName`；`parseSqlResult0`（resultMap 路径）也存入 `ResultTypeName` 保持对称
3. **[orm/result_convert.go](orm/result_convert.go)**：`getResultType` 增加 `ResultTypeName` 分支：
   - `ResultM != nil` → 已有路径（createModel）
   - `ResultM == nil && ResultTypeName != ""` → `gCache.createModel(GetShortName(ResultTypeName))`，成功则返回解析后的类型，失败 fallback 到 `ResultT`
   - `ResultM == nil && ResultTypeName == ""` → 返回 `ResultT`（旧行为）
4. **[orm/return_type.go](orm/return_type.go)**：`checkSql` 中 `resultType` 路径，当 `f.Result.ResultTypeName` 非空时，先尝试 `gCache.createModel` 获取真实类型再与 Go 返回类型比较；解析失败时降级为短类名比较（字符串匹配，与 resultMap 路径对称）
5. **[types/common.go](types/common.go)**：`parseResultTypeFrom` 的 default 分支日志降为 `Debugf`（已知非 JDBC 类型不再刷 warning 噪音）

**不变式**：`ResultT` 始终保留 `parseResultTypeFrom` 的急切解析结果（向后兼容），`ResultTypeName` 是新增的补充字段。

### M-07：分页支持

**核心思路**：Go 语言无 ThreadLocal，采用 `PageParam` 参数约定 + 代理层检测 + SQL 改写器注入 `LIMIT/OFFSET` + `SELECT COUNT(*)` 获取总数。

**新增文件：**

1. **[orm/page.go](orm/page.go)**（新建）：
   ```go
   // PageParam 分页参数（传入 Mapper 方法作为首参或任意位置参数）
   type PageParam struct {
       PageNum  int // 页码（从 1 开始）
       PageSize int // 每页条数
   }
   func (p *PageParam) Offset() int { return (p.PageNum - 1) * p.PageSize }
   func (p *PageParam) Limit() int  { return p.PageSize }
   func (p *PageParam) Valid() bool { return p.PageNum > 0 && p.PageSize > 0 }

   // Page 分页结果
   type Page struct {
       Total    int64
       Records  []map[string]interface{}
       PageNum  int
       PageSize int
   }
   ```
   - `PageParam` 是轻量参数结构，代理层检测后提取
   - `Page` 返回总条数 + 当前页数据 + 分页元信息
   - Mapper 方法签名：`func(page *orm.PageParam, params map[string]interface{}) (*orm.Page, error)`

2. **[orm/sql_rewrite.go](orm/sql_rewrite.go)**（新建）：
   ```go
   // applyPagination 在 SQL 尾部注入 LIMIT/OFFSET
   func applyPagination(query string, limit, offset int) string
   // buildCountSQL 将 SELECT ... FROM ... 转为 SELECT COUNT(*) FROM ...
   func buildCountSQL(query string) string
   ```
   - `applyPagination`：检测已有 LIMIT 则替换，否则追加 `LIMIT $1 OFFSET $2`（由 `formatSQL` 转换占位符）
   - `buildCountSQL`：复用 `table_prefix.go` 的 tokenizer，剥离 ORDER BY/LIMIT/OFFSET/RETURNING，将 SELECT 列表替换为 `COUNT(*)`
   - 纯函数，可单测

**改动点：**

3. **[orm/proxy_arg.go](orm/proxy_arg.go)**：`ProxyArg` 新增 `PageParam *PageParam` 字段，`buildArgs()` 提取 `*PageParam` 并从 `Args` 中移除（避免作为 SQL 参数传递）
4. **[orm/base_mapper.go](orm/base_mapper.go)**：新增 `executePage` 方法：
   - 调用 `buildCountSQL` 生成 COUNT 查询 → `DB.QueryContext` 获取 `Total`
   - 调用 `applyPagination` 注入 LIMIT/OFFSET → 正常执行获取 `Records`
   - 组装 `Page` 返回
5. **[orm/orm_cache.go](orm/orm_cache.go)**：代理闭包检测 `*PageParam` 参数（检查 `ProxyArg.PageParam != nil`），路由到 `executePage` 而非 `executeMethod`
6. **[orm/database_connection.go](orm/database_connection.go)**：`QueryContext` 中 `applyPagination` 在 `applyTablePrefix` 之后、`formatSQL` 之前执行（如果调用方已注入则跳过）
7. **[types/table_struct.go](types/table_struct.go)**：更新 `selectPage` codegen：
   - 生成签名从 `func() ([]T, error)` 改为 `func(page *orm.PageParam) (*orm.Page, error)`
   - XML `selectPage` 语句保持全表查询（LIMIT/OFFSET 由框架注入）
8. **[types/mp_builtin.go](types/mp_builtin.go)**：`ensureMPBuiltinCRUD` 中 `selectPage` 方法签名更新

**执行流程**：
```
mapper.SelectPage(&PageParam{PageNum:2, PageSize:20}, params)
  → proxy 闭包检测 PageParam → 提取 → executePage
  → buildCountSQL(baseSQL) → COUNT 查询 → Total
  → applyPagination(baseSQL, 20, 20) → LIMIT/OFFSET 查询 → Records
  → 组装 Page{Total, Records, PageNum, PageSize} 返回
```

**方言兼容**：所有 4 种数据库（MySQL/SQLite/PG/KingbaseES）均原生支持 `LIMIT n OFFSET m`，无需方言分支。

### 4.3：`<if test>` 字段引用注册期校验

**核心思路**：在 `RegisterMapper` → `bindSqls` 阶段，对已解析的 SQL 函数中所有 `<if test>` 条件引用的字段名，与 `parameterType` 对应的已注册 model 字段做交叉校验，缺失字段打 warning 日志。

**改动点：**

1. **[types/sql_fragments.go](types/sql_fragments.go)**：新增导出函数 `CollectIfTestFieldNames(items []SqlFragmentItem) []string`：
   - 递归遍历 `ifTestSqlFragment`/`chooseSqlFragment` 的条件列表
   - 提取每个 `ifCondition.CheckName`（去除 `.length` 后缀、`params.` 前缀等）
   - 去重返回字段名列表
   - 此函数在 `types` 包内，纯数据提取，不依赖 orm

2. **[types/sql_function.go](types/sql_function.go)**：`SqlFunction` 新增 `IfTestFields []string` 字段，在 `parseSqlFunctionFromXmlNode` 中调用 `CollectIfTestFieldNames` 填充

3. **[orm/mapper_cache.go](orm/mapper_cache.go)**：`funcInfo.bindSql` 中，绑定成功后调用 `validateIfTestFields`：
   - 从 `SqlFunction.IfTestFields` 获取字段名列表
   - 若 `SqlFunction.Param.TypeName` 非空且非 JDBC 基础类型，尝试 `gCache.createModel(TypeName)` 获取 model `reflect.Type`
   - 反射遍历 model 的导出字段，`buildKey` 小写匹配
   - 缺失字段打 `Warnf("[if-test] %s.%s: field %q not found in model %s, may produce empty WHERE", ...)`

4. **[types/mp_builtin.go](types/mp_builtin.go)**：`jdkTypeNames` 集合已定义 JDBC 基础类型名，用于跳过非自定义类型的校验

**注意**：
- 校验结果仅打 warning，不阻塞注册（与 `SetStrictRegister` 正交）
- `params.xxx` 路径跳过校验（通用 map 参数，无法静态检查）
- camelCase / PascalCase 差异由 `buildKey` 小写统一解决

## Risks And Compatibility

- **M-04 向后兼容**：`ResultTypeName` 是新增字段，零值为空字符串，不影响现有 `ResultT` 路径；`parseResultTypeFrom` 日志降级不影响功能
- **M-07 代理层改动**：`ProxyArg.buildArgs()` 增加类型检测分支，仅当 `*PageParam` 存在时生效，不影响非分页方法
- **M-07 codegen 签名变更**：`selectPage` 签名从 `func() ([]T, error)` 变为 `func(*PageParam) (*Page, error)`，**破坏现有 codegen 用户**——需在 release notes 中标注。首版返回 `*Page`（records 为 `[]map[string]interface{}`），泛型 `Page[T]` 留待后续
- **4.3 仅 warning**：不改变注册/运行行为，零功能风险
- **SQL 改写器边界**：`buildCountSQL` 需正确处理子查询、CTE、UNION、DISTINCT 等复杂 SQL；首版覆盖常见 SELECT 形态，复杂 CASE 记录已知限制
